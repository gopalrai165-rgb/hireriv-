# Languages (Step 67)

Hireriv is in English and Hindi. Telugu has a partial locale. Tamil, Bengali and Marathi are ready to add: the code knows their names, script fonts and digits, but they have no locale file yet. This page explains how languages work, how to add one, and how translations are reviewed.

> **The Hindi text is a draft.** It was written for this step and has not yet been checked by a native speaker who knows recruitment words. It must be reviewed (section 5) before launch. Telugu is incomplete: anything missing shows in English.

> The Step 69 words (near me, popular jobs, cities, mobile sign-in, Call HR) were added to `hi.json` as a draft too and are part of the same review.

## 1. How the language is chosen

In this order:

1. `?lang=hi` in the address. On a GET, this also saves the choice in the cookie, so shared links open in the sender's language.
2. The `hr_lang` cookie. It lasts a year, is httpOnly and SameSite=Lax, and holds only the language code.
3. For a signed-in candidate, the language saved on their profile (`candidates.language`). It is set from the language buttons and from Account settings → Language.
4. English.

The browser's `Accept-Language` is **never** used on its own: people on shared or borrowed phones often have a browser language they did not choose. Pages send `Vary: Cookie`. Non-English pages have a canonical address with `?lang=` and `hreflang` links to every offered language plus `x-default`, so search engines index each language.

The selector is a form in the header and the mobile menu (`POST /language`). It works without JavaScript. Each button is labelled in its own language (`lang="hi"`), the current one has `aria-current`, and the form redirects only to an internal path (`safeBack` in `i18n.js`).

Which languages are offered is set by `LANGUAGES` in `.env`. The default is `en`: English only, with no language selector, no Hindi versions for search engines, and `?lang=hi` or an old language cookie showing English. `LANGUAGES=en,hi` turns Hindi back on (after the native-speaker review in §5). Only languages that have a locale file are offered.

## 2. Where the words live

- `locales/en.json` is the source, with nested **stable keys** (`apply.submit`, `jobs.filters.type`). Templates call `t('key', {vars})`. Text is never written into a template for the translated pages.
- `locales/<code>.json` has the same keys. Anything missing falls back to English, key by key.
- Plurals are `{ "one": "…", "other": "…" }`, chosen with `Intl.PluralRules`. Placeholders are `{name}`.
- `values.<group>` translates stored values (job type, work mode, shift, category, experience). **Stored data stays in English**: filters, search, the API, exports and matching all see the same value whatever the interface language.
- `phrases` translates messages built on the server, such as validation errors and page titles, through `tm()`.
- `js` holds the words the browser scripts show. They are sent inside the page as JSON (`#i18n-strings`), so no extra request is made, and only the page's own language is sent.
- `search` holds words typed in that language and what they mean (section 3).
- Numbers, dates and money use `Intl` with the language's region (`hi-IN`). For example ₹1,25,000. Native digits are accepted in search but not printed, because most job seekers expect 0-9 for pay and phone numbers.
- Script fonts (Noto Sans Devanagari, Telugu…) load only on pages in that language. Hindi and Telugu get more line height so vowel signs are not clipped.
- **Never translated:** company names, job ids, application references, email addresses, URLs, people's names, and anything an employer typed (unless they approved a translation, section 4).

What is **not** translated yet: the employer workspace, the Admin pages and emails. Those pages say so: their `<main>` carries `lang="en"`, so screen readers use an English voice. The candidate account pages are partly translated.

## 3. Searching in other languages

`i18n.searchTerms()` runs before the normal search:

- Text is normalised to NFC.
- Zero-width joiners are dropped.
- Devanagari and Telugu digits become 0-9.
- Each locale's `search.terms` and `search.places` map words to the English search word or to a filter. For example "ड्राइवर दिल्ली" becomes the keyword driver with the location Delhi. "पार्ट टाइम" becomes the Part-time filter.

Every locale's words are used whatever the interface language, so Hindi typed on the English site works too. Words with no mapping are searched as typed, which finds approved translations (below) and anything an employer wrote in that language. The search box says "We understood: …" when it changed something.

## 4. Job listing translations

Employers translate their own listings under Jobs → (language) (`job-translations.js`, collection `job-translations`):

1. **Draft.** The AI assistant (`ai-assistant.js`, feature `job-translation`) drafts from the original. When the AI is off, the original is copied for the employer to write over. Nothing is shown to candidates yet.
2. **Checks**, run on every save:
   - Blocking: a number in the original that is missing, a number that was added, a new link, or an empty title or description.
   - To check: different list lengths, text left in English, and words the AI marked as unclear.
   Pay, dates, hours, counts and qualifications must be the same. The AI is told not to convert salaries, invent local qualifications or add terms.
3. **Approve.** The employer ticks "I checked this against the original". The approved text becomes a numbered version, with who approved it and when, recorded in the company activity log.
4. **On the job page**, people using that language see the approved title, description and lists. The original is one click away (a `details` element in English), and the facts (pay, place, type, dates, skills) always come from the original listing. A note says who translated it and when.
5. **When the listing changes**, the translation is hidden again: each version stores a hash of the original it was made from. The employer sees "Needs approval again".
6. **Withdrawal.** The employer can withdraw a translation. The team can withdraw any translation for a reason (moderators, `jobs.moderate`), recorded in the trust audit history. The team translates only listings it posted itself.

Approved text is searchable.

## 5. Reviewing the interface words

Before a language goes live, and after every change to its locale file:

1. A native speaker who also knows Indian recruitment words checks the whole file in context (`?lang=hi` on every public page, the apply form and the account pages). The glossary page (`/help/job-terms`) is the reference for words like CTC, in-hand, PF and notice period.
2. Keep to plain, everyday words. Use the English word where people really use it ("ड्राइवर", "शिफ़्ट", "रिज़्यूमे"), and write it in the script.
3. Check that numbers, placeholders (`{count}`) and links are unchanged: `test/i18n.test.js` fails if a key or placeholder is missing.
4. Record the reviewer and date in the commit message, and change the note at the top of this page.

**Glossary.** These terms must be the same everywhere: नौकरी (job), आवेदन (application), वेतन (pay), इन-हैंड (in-hand), सीटीसी (CTC), शिफ़्ट (shift), अनुभव (experience), फ़्रेशर (fresher), नोटिस पीरियड (notice period), रिज़्यूमे (resume).

## 6. Adding a language

1. Copy `locales/hi.json` to `locales/<code>.json` and translate it. Partial files work, because English fills the gaps.
2. If the language is not already in `LANGUAGES` in `i18n.js`, add it with its name, native name, tag, script and Google font.
3. Add its digits to `DIGITS` in `i18n.js` if it has its own.
4. Add `search.terms` and `search.places` for common job words and big cities.
5. Add it to `LANGUAGES=` in `.env`.
6. Add the language to the checks in `test/i18n.test.js` and `test/accessibility.test.js`.

No template changes are needed.

## 7. Voice and the simpler apply journey

- **Listen to this job** uses the browser's own speech (`speechSynthesis`) in the page's language. It is shown only where the browser has it.
- **Speak instead of typing** (the microphone next to message boxes) uses the browser's speech recognition. Before first use it asks, saying that the browser's maker may receive the audio and that Hireriv does not record it. That agreement is remembered on the device only. The words go into the box to check and edit; nothing is sent until the person sends the form. `VOICE_INPUT=0` turns it off, and the site's Permissions-Policy then refuses the microphone entirely.
- **Applying:**
  - The form shows everything entered for checking before it is sent.
  - Errors stay at the top of the form, are read out, link to each field and mark it invalid.
  - What was typed is kept in this tab (sessionStorage, never files) until it is sent or the person signs out, so a reload or dropped connection loses nothing.
  - A resume stays optional wherever the job allows it.
- Proficiency in English, spelling or grammar is **never** a factor in matching or ranking (`job-match.js` has no such factor). The language someone uses on the site is not shown to employers.

## 8. Analytics

Two counts are added to the website analytics (`site-analytics.js`):

- `language-selected`, with the language chosen
- `application-language`, the interface language when an application was sent

They follow the existing rules: no personal data, and counted only where analytics consent allows. They show whether people in each language finish applying.

# Hireriv – Staffing & Recruitment Website

A complete website for a tech-driven staffing and recruitment company, built with Node.js, Express and EJS.

## Features
- **Design**: blue and white (#123B70 primary blue, #2878D4 action blue, #F3F6FA light background) with the Inter font. Text and buttons use #1F6BC2, a slightly darker action blue, so they pass WCAG AA contrast. Every link, button and field shows a clear focus ring for keyboard users
- **Header**: Hireriv by Raigozen logo, Find Jobs, Job Categories, Staffing Solutions, Employers, Career Resources and Saved, a **Login** menu (job seekers or employers) and a **Post a Job** button (`/post-a-job`: signed-in employers go straight to the job form, everyone else to employer sign-up). On phones it all folds into the menu button
- **Home**: hero ("Find Your Next Opportunity. Build Your Future.") with search by job title or skill, location and category, animated stats, **job categories** with live job counts, featured jobs (real openings first), an **employer section** (Post a Job, Find Candidates, Bulk Hiring, Permanent Recruitment, Contract Staffing), industry tabs, 6-stage process, testimonials, FAQ, blog preview and CTAs. Sample testimonials show until you add real ones (or hide the section) under Admin → Settings → Homepage testimonials, and the dashboard reminds you until then. Every page has a skip-to-content link for keyboard and screen-reader users
- **Job Categories** (`/categories`): 12 groups (Office jobs, Skilled & field jobs, IT & Engineering, Healthcare, Manufacturing, Logistics & Delivery, Construction, Retail, Hospitality, Sales, Finance & Banking, Fresher jobs) with open-job counts, each opening Find Jobs filtered to that group (`/jobs?group=…`), then every category listed by kind of work
- **Sample jobs**: the starter jobs that come with the site are examples, not real vacancies. They show a **Sample** label, can't be applied to, send no job alerts, and stay out of Google for Jobs and the sitemap. The dashboard reminds you to replace them; editing one in Admin → Jobs makes it a real job
- **Job search** (`/jobs` and the JSON API `GET /api/jobs`): every word of the keyword must appear in the title, skills, company, category or description, with title matches ranked first. Filter by city, **state** or remote, **several categories** at once, **experience level** (fresher, entry 0–2, mid 3–7, senior 8+ years, from each job's experience range), **minimum pay** (a month; daily and yearly pay are compared at 26 days and 12 months), job type and work arrangement, and sort by relevance, newest or highest pay. Results are in a stable order (date, then id), so pages never repeat or skip a job. When nothing matches, each active filter is shown with a link that removes it. `GET /api/jobs` takes the same filters (also as `keyword`, `city`, `state`, `employmentType=full_time…`, `workArrangement=remote…`), `page` and `limit` (20 by default, 50 at most), refuses bad values with a 400, returns only open, published jobs within their application period (no sample listings), and is limited to 120 requests a minute per IP; `GET /api/jobs/:id` returns one job
- **Employer sign-up** (`/employer/register`, or `POST /api/employers/register`; **Post a Job** leads here when signed out): company name, industry, size, website, where they hire, city and state, an optional **GSTIN** (format and check character validated), the contact's name, mobile and work email, a password (at least 10 characters, scrypt-hashed) and agreement to the Terms, the **Job posting rules** (`/job-posting-policy`) and the Privacy Policy. The account works once the email is confirmed (24-hour link); the same reply is given for emails that already have an account. Personal mailboxes (Gmail, Yahoo…) are allowed but flagged for the team. The team **verifies** each self-signup company (separately from approving its jobs) under Admin → Clients; companies the team invited are verified already, and verified companies get the **Verified employer** badge
- **Employers posting jobs** (portal **Jobs**, or the JSON API `POST/GET /api/employers/jobs`, `PATCH /api/employers/jobs/:id`, `POST /api/employers/jobs/:id/submit`, `POST /api/employers/jobs/:id/close`; the older `/api/jobs` addresses still work): kind of work, category, city, workplace address and walk-ins, work arrangement, employment type, number of openings, shift, working hours and days, experience, education, pay range per month/year/day/hour (blank shows "Not disclosed"), description, responsibilities, requirements, who can apply, skills, benefits and the last day to apply. Jobs start as drafts; sending one for review emails the team, who **approve** it (only for verified companies) or **send it back** with what to change, and the person who posted it and the company owners are emailed either way. Companies that signed up themselves need the poster's **mobile verified** (a 6-digit text-message code) before a job can be sent, may have up to 5 jobs waiting while unverified, and up to 50 live, paused or waiting. Live jobs can be **paused** (hidden, back in one click), resumed or closed; changing a live job sends it back for review. Drafts, waiting, sent-back and paused jobs never appear on the site, the API, the sitemap or share images. The admin dashboard lists jobs and companies waiting for review
- **Resume safety**: every uploaded resume must really be a PDF, DOC or DOCX (its first bytes are checked, not just the name) and under 5 MB. Set `CLAMAV_HOST` (and `CLAMAV_PORT`, default 3310) to a ClamAV `clamd` and every resume is scanned before it is saved; infected files are refused and deleted, and if the scanner can't be reached uploads are refused rather than let through. Resume downloads (team, candidate and client) need the sign-in **and** a signed link from the page that expires after 15 minutes, so a copied or forwarded link stops working
- **One application per person per job**: besides the check when applying, the database itself refuses a second live application for the same person (email, or mobile number when there's no email) and job; withdrawn applications don't count. Duplicates made before this rule were marked once (the one furthest along is kept; the others show a **Duplicate** pill)
- **Job addresses**: jobs live at `/jobs/<title>-<city>-<id>` (e.g. `/jobs/full-stack-developer-mern-bengaluru-hr-101`), used in links, the sitemap, Google for Jobs data and share buttons. The id finds the job, so `/jobs/hr-101` still works (pointing search engines to the full address) and an address with an old title moves to the current one
- **Pay as numbers**: each job's pay is a minimum and/or maximum in rupees per month, year, day or hour, plus an optional note ("+ PF & ESI"), or left blank when not disclosed. The minimum can't exceed the maximum. Yearly pay of ₹1 lakh or more shows as LPA. Existing jobs' salary text was read into numbers once on upgrade
- **Job details**: workplace with its state, pay (or "Not disclosed"), experience, education, work schedule, qualifications, benefits, closing date, a **Verified employer** badge when the job is linked to an active client account, and **Report this job** (fake, asks for money, misleading, filled, discriminatory). Reports are emailed to the team and listed under Admin → Inbox → Reported jobs. A job past its closing date stops taking applications at once, even before the hourly check closes it
- **Find Jobs** (`/jobs`): office, skilled and field jobs side by side. Tabs for each **kind of work** (Office & professional, Skilled & technical, Industrial, field & service) with job counts, plus keyword, category (grouped by kind of work), location, work-mode (On-site, Hybrid, Remote, Field work, Client site) and job-type filters, job detail pages, and online applications with resume upload. **Quick apply** for skilled and field jobs: a name and mobile number are enough (email, resume and skills are optional extras), the recruiter calls back, and an **Apply on WhatsApp** button opens a chat with your team pre-filled with the job (shown once a real WhatsApp number is saved in Settings). Office jobs still ask for a resume and email, and the job form's **Resume** setting can switch any single job either way. People without an email are matched by mobile number (+91 98765 43210 and 09876543210 count as the same), so applying twice still updates one application, and the Talent pool and data retention treat each number as one person. Candidates without an email can't use My applications yet. If someone applies again for a job they already applied to, their existing application is updated with the new resume and details (stage, notes and history are kept) and the team is told, instead of a second candidate appearing. Someone who withdrew and re-applies gets a fresh application
- **Services** (`/services`): an overview with a "which one fits" guide, and a page for each of the six services (Permanent Staffing, Contract & Temp Staffing, Executive Search, Bulk & RPO Hiring, Background Verification, Corporate Training) covering what's included, who it suits, how it works, how billing works and FAQs. Each page has Google Service and FAQ structured data, and its "Share a requirement" button pre-selects the service on the hire form
- **Industries** (`/industries`): a page for each of the ten specialist desks with the roles hired, what recruiters screen for, related services and that desk's live open jobs. All service and industry wording lives in `catalog.js`, and the homepage, footer, hire form and sitemap follow it
- **Hire a Team** (`/hire`): employer requirement form, engagement models and the hiring process
- **Privacy Policy** (`/privacy`) and **Terms of Use** (`/terms`), written for India's DPDP Act 2023, linked from the footer and from every form that collects personal data. They pull your email, phone and address from Admin → Settings. Change `LEGAL_UPDATED` in `server.js` when you edit either page
- **About**, **Blog** (with articles) and **Contact** pages
- Newsletter signup, a floating WhatsApp button, and a mobile-responsive layout
- **Job alerts** (`/jobs`): candidates pick a category and/or city, confirm by email (double opt-in), then get an email the first time each matching job goes live. Remote jobs match every city. Every alert has a one-click unsubscribe, and subscribers are listed under Admin → Job alerts
- **More search filters** (`/jobs` and `GET /api/jobs`): **skills** (`skill=Forklift&skill=Safety` or `skills=Forklift,Safety`, up to 5, each one required, any letter case), **company** (the exact name, any letter case) and **shift** (Day, Night, Rotational, Flexible). When a keyword search finds nothing because of a typing slip, it is tried once more with the closest words from the live jobs ("forklfit operater" → "forklift operator"); the page says so and the API returns `correctedQuery`. Jobs can list **must-haves** (licences or certificates, starting straight away, the physical work involved) under Requirements on the job page and in the API's `requirements`. They're shown to candidates, never scored
- **Explainable matching** (`job-match.js`): for a signed-in candidate, each job page shows **How you match**, a score from 5 work factors with what counted: skills (40%), experience (20%), location (15%), pay (15%) and job type and shift (10%). Admins change the weights under Settings → Job matching (whole numbers adding up to 100). Anything the candidate or the job hasn't stated is left out of the score instead of counting against them; with too little known it says "Not enough details yet". Only work details are used, never name, age, gender, photo or anything like them. Scores help people sort and are never used to turn anyone away. `GET /api/jobs/:id/match`
- **Recommended jobs** (`/account/recommendations`, also on the dashboard; `GET /api/candidate/recommendations`): open jobs that fit the candidate's profile, preferences and saved searches, with reasons ("Fits your saved search", "In a category you chose", "Like jobs you saved") and the match explanation. Jobs they already applied for or saved are left out
- **Saved searches** (`/account/saved-searches`; `GET/POST /api/candidate/saved-searches`, `PATCH/DELETE /api/candidate/saved-searches/:id`): **Save this search** on Find Jobs keeps every filter, with a name and an email choice: straight away, a daily summary or a weekly summary (or none). Up to 20 each, checked like a search. Older job alerts appear here too. Unsubscribing from an email stops the emails and keeps the search. Summaries are checked every hour (`SAVED_SEARCH_SCAN_MS`) and count towards the daily alert limit
- **Profile from your resume** (`/account/resumes/:id/review`; `POST /api/candidate/resumes/parse`): the candidate picks one of their resumes and sees the skills, jobs (title, company, dates) and education read from it, unticks or corrects anything, then adds what they kept. Nothing is saved before that, and the resume file stays as it was uploaded. The API also reads a file sent just for that (checked by type, size and virus scan, then deleted); unreadable files get a 422, too large a 413, and anything that isn't a real PDF or Word file a 400. Reading is limited to 20 every 10 minutes
- **Find candidates** (`/employer/candidates`; `GET /api/employers/candidates`): owners, hiring managers and recruiters of **verified** companies can search candidates who chose "Let verified employers find my profile" in their account settings (off unless they turn it on). Results show a first name and initial, skills, experience level, city, education level, recent job titles (without employers), the work they want and when they can start. Never email, phone, resume or past employers. Filter by keywords, skills, location, experience, job type, shift and availability, and sort by match with one of the company's own open jobs. **Invite to apply** (`POST /api/employers/candidates/:id/invites`) sends the candidate a notification and email about one of the company's open jobs; once per candidate and job, 30 a day per company, recorded in the company's activity log. The candidate decides whether to apply, and their contact details reach the company only then. Applicants can also be sorted by skill match on the Applicants page
- **Agency and staffing** (`/admin/workspace`, linked as **Agency & staffing** in the admin bar):
  - **Team roles**: Super Admin (stored as Admin), Recruitment Manager, Recruiter, Account Manager and Finance Manager, set on the Team tab. Every page and API checks the signed-in person's role on the server (`agency-roles.js`). Recruiters see only requisitions assigned to them; Account Managers change only the clients they look after; fees, rates and revenue show only to Super Admins, Account Managers and Finance Managers; a Finance Manager opens only billing pages (placements, invoices, payments, credit notes, invoice drafts, money reports) and no candidates, jobs or applications. Client employers and candidates keep their own sign-ins
  - **Clients** (`/admin/clients/:id`): each client gets an account manager (Admins assign) and **contracts** with their terms written exactly: permanent fee as a % of annual CTC or a fixed amount, guarantee days, payment days and an optional staffing markup. There is no built-in commission rate: placements for a client's requisition take their fee and guarantee from the active contract, else from Settings
  - **Requisitions** (`/admin/requisitions`): a client's request to fill a number of openings (permanent, temporary or contract), with location, skills, budget, bill and pay rates, priority and a fill-by date. Linked to the client's job, its applicants form the pipeline; placements recorded for that job count towards it, and it closes as Filled when the last opening is placed. Statuses move only Requested → Open → On hold / Filled / Cancelled (a reason is needed to cancel); every change is in its history. Recruitment Managers assign recruiters, who are notified. A client's portal request becomes a requisition with one click
  - **My workspace** (`/admin/workspace`): the signed-in person's requisitions by priority and due date, their placements and workers, and the team's workload for managers (heavy loads flagged)
  - **Staffing assignments** (`/admin/staffing`): where temporary and contract workers are deployed: site, dates, shift, bill and pay rates. One worker can't have overlapping assignments; statuses go Scheduled → Active → Completed or Ended early. Placements can now be **Temporary**, and billed **per staffing assignment**
  - **Invoice drafts** (`/admin/invoice-drafts`): the team asks for an invoice (a placement's fee once the candidate has joined, or a staffing period: days or hours worked × the bill rate); an Admin or Finance Manager issues it as a numbered GST invoice through the existing billing, and payments are recorded afterwards as before. The same fee or period, or the same `Idempotency-Key`, always gives the same draft, and issuing twice returns the first invoice. Money is kept in whole paise and percentages in basis points, so amounts are exact
  - **Reports** (`/admin/recruitment-reports`): open requisitions and openings left, placements, median days to fill, fill rate, overdue and stale requisitions, placements by type, workers on assignment, workload and results by client (with billing for money roles). **Audit log** (`/admin/agency-audit`): every change to contracts, account managers, requisitions, assignments and invoices, with who made it
  - **For clients** (`/employer/requisitions`): request people, follow how many are filled and who has been shortlisted, and see workers deployed. Only the company's own requisitions, never pay or bill rates
  - JSON: `GET /api/clients`, `GET /api/clients/:id`, `PUT /api/clients/:id/account-manager`, `POST /api/clients/:id/contracts`, `PATCH /api/contracts/:id`, `GET/POST /api/requisitions`, `GET/PATCH /api/requisitions/:id`, `PUT /api/requisitions/:id/recruiters`, `GET /api/placements`, `GET/POST /api/placements/:id/invoices`, `POST /api/placements/:id/invoices/:draftId/issue`, `DELETE /api/placements/:id/invoices/:draftId`, `GET/POST /api/staffing/assignments`, `PATCH /api/staffing/assignments/:id`, `GET /api/recruitment/reports`, `GET /api/recruitment/audit`, and for clients `GET/POST /api/employers/requisitions`, `GET /api/employers/requisitions/:id`. Short links: `/recruiter/workspace`, `/recruiter/placements`, `/staffing/assignments`, `/client/requisitions`, `/client/candidates`
- **Workforce** (`/admin/workforce`, linked from Agency & staffing): temporary and contract workers after placement (`workforce.js`):
  - **Onboarding**: a temporary or contract placement becomes a worker in one click. The worker is the placed candidate's own account (by email); nothing is copied from their profile. Joining steps come from a list for the client and role, the client, or the default (any government photo ID the worker chooses, an emergency contact, the site rules). Identity numbers and bank details can't be made a condition of joining. The worker completes the steps under **My work** (`/account/work`); documents are PDF, JPG or PNG checked by their content (and scanned when ClamAV is set), kept outside the public folder, opened only through 15-minute signed links by the worker and Admins or Staffing Managers, and every opening is logged. Statuses: Onboarding → Ready to join (all required steps done) → Joined → Left. Documents with an expiry date are flagged before they expire and marked Expired after
  - **Assignments** gain the client's approved **sites** (each with a time zone), a **site supervisor** from the client's team, shift times, break and late-arrival grace. One person can't have overlapping assignments at any client or two shifts at once. Extensions are recorded; clients ask for **replacements** and the staffing team arranges or declines them
  - **Shifts** (`/admin/workforce/shifts`): planned per day inside the assignment, never twice
  - **Attendance**: check-in, breaks and check-out by the worker (server time, no location ever collected), by their supervisor, or by the team; sites without a connection enter times by hand from their register, up to 7 days back, marked and logged. Times are stored in UTC and shown in the site's time zone. Late arrivals beyond the grace, absences and overtime are recorded. A check-in without a check-out becomes an **exception** after the shift (no hours are ever invented), fixed only by a correction
  - **Corrections and overtime** are approved by someone other than whoever asked for them or entered the times; requests and decisions are never edited, and the record keeps its original times and full history
  - **Timesheets** (`/admin/workforce/timesheets`, plus weekly hours): submitted for up to 31 finished days, refused while check-ins, exceptions, corrections or overtime are open; the same period is the same timesheet. Approved by a supervisor or the staffing team, never by whoever submitted it. Approval locks the attendance and asks Finance for an **invoice draft** (days or hours × the bill rate), which Finance issues as before. **Payroll** (`/admin/workforce/payroll`, CSV): approved timesheets at the agreed pay rate, for Admins and Finance Managers
  - **Roles**: Staffing Managers run all of it; Account Managers for their own clients; Recruiters see onboarding status only; Finance Managers see approved timesheets and payroll only. At the client, owners and hiring managers see and approve for all their workers, **Site supervisors** (a new employer role) only for the assignments they supervise and nothing else in the portal, viewers see without changing (`/employer/workforce`). Clients never see pay rates, emails, documents or emergency contacts
  - **Rules** (`/admin/workforce/rules`, Admins): overtime threshold and minimum, the standard day, when a missing check-out becomes an exception, the longest shift, how far back times may be entered, and reminder timings
  - **Reminders** through the notification service, under a new **Work & attendance** email preference: joining steps, documents to review or expiring, next shift, missing check-ins and check-outs, timesheets waiting or sent back, assignment changes and ends, contracts ending, replacement requests. The checks run every hour (`WORKFORCE_SCAN_MS`); each reminder has a stable key, so it's sent once
  - JSON: `GET/POST /api/staffing/workers`, `GET /api/staffing/workers/:id`, `GET/POST /api/staffing/workers/:id/onboarding`, `POST /api/staffing/workers/:id/documents`, `GET/POST /api/staffing/shifts`, `POST /api/staffing/attendance/check-in`, `POST /api/staffing/attendance/check-out`, `POST /api/staffing/attendance/:id/breaks`, `POST /api/staffing/attendance/absences`, `GET /api/staffing/attendance`, `POST /api/staffing/attendance/:id/overtime`, `POST /api/staffing/attendance/:id/corrections`, `POST /api/staffing/attendance/corrections/:id/approve` (and `/reject`), `GET/POST /api/staffing/timesheets`, `POST /api/staffing/timesheets/:id/approve` (and `/reject`), `PUT /api/staffing/clients/:id/sites`, `GET/PUT /api/staffing/requirements`, `POST /api/staffing/assignments/:id/replacement`. Short links: `/staffing/workers`, `/staffing/onboarding`, `/staffing/shifts`, `/staffing/attendance`, `/staffing/timesheets`, `/worker/dashboard`, `/client/workforce`
- **Saved jobs** (`/saved`): a bookmark button on every job card and job page, with a count in the header. Saved jobs are stored in the visitor's browser, so no account is needed. Closed jobs stay listed and marked Closed, and deleted jobs drop off automatically
- **Spam protection**: every public form has a hidden bot trap and a per-IP limit (5–6 submissions per 10 minutes), and the admin locks out an IP for 15 minutes after 10 wrong passwords. Behind a reverse proxy, set `TRUST_PROXY=1` so limits apply per visitor
- **Share a job**: WhatsApp, LinkedIn, copy-link and the phone's share sheet on every open job, using the public `SITE_URL` address. Shared links show a branded **preview image**: each job gets its own (title, company, city, work mode, experience and salary), and every other page shows the site image with your tagline. Images are drawn on the server (`og.js`, fonts in `assets/fonts`) and change automatically when a job is edited
- **Job-seeker accounts** (`/account/register`, linked as **Register** in the header): name, email and mobile number (city, experience, notice period, skills, LinkedIn and a resume are optional), plus agreement to the terms. The welcome email has a link that opens the account (valid 24 hours), so only the owner of the address gets in; registering again with the same email updates the profile and gives the same reply, so the form can't reveal who has an account. A registration is stored as a general application with the source "Candidate account", so the team is emailed and sees new sign-ups in Applications and the Talent pool like any CV. Signed in, candidates get **one-click apply** on every job page using their saved profile (each application gets its own copy of the resume; office jobs need a resume on file first), **Jobs for you** (open jobs matching their skills, then their city or remote), **job alerts** they can add and remove (on at once, as the email is already confirmed), resume upload and replacement, and name and phone in the profile. Signed in, saved jobs are also kept in the account (`/api/candidate/saved-jobs`), merged with the ones on the device, so they follow the candidate to other devices; the header shows **My account** instead of Register
- **Candidate accounts, full version** (Step 49; the planned `/candidate/*` addresses redirect to `/account/*`):
  - **Signing in:** an emailed link, or an optional password (set in Settings after the email is confirmed; at least 10 characters, scrypt-hashed). Eight wrong passwords for one email pause password sign-in for 15 minutes, and wrong passwords and unknown emails get the same reply. **Forgot password** emails a 30-minute one-time link. Setting, changing or resetting the password emails a notice and signs out every other session. After signing in, people return to the page they were going to, but only to the site's own candidate pages and job pages (`?next=` is checked).
  - **Profile** (`/account/profile`): basic details with state, the jobs, places, job types, work arrangements and shifts wanted, expected pay, notice period or start date, skills, certificates, languages, work experience and education, each section saved on its own, and a **completion meter** with the next things to add. Nothing beyond name and mobile is required, and there are no fields for Aadhaar, PAN, bank details or date of birth.
  - **Resumes:** up to three, choose which one is sent with applications, delete (applications already sent keep their copy). Files are checked before saving and downloads use 15-minute signed links.
  - **Other pages:** **Saved jobs**, **Interviews** (coming up and earlier) and **Settings**: password, whether recruiters may find the profile for other jobs (off removes them from the Talent pool), WhatsApp, SMS and news opt-ins, recent account activity (kept 12 months), sign out on all devices, download or delete the account.
  - **JSON API:** `POST /api/auth/register`, `/api/auth/login`, `/api/auth/logout` and `/api/auth/verify-email`; `GET` and `PATCH /api/candidate/profile` (unknown fields are refused); `POST /api/candidate/resumes` and `DELETE /api/candidate/resumes/:id`; and `DELETE /api/candidate/account`. Responses never include password hashes, session tokens or file names, only signed download links.
- **My account** (`/account`): candidates sign in with a one-time emailed link (no password) using the email they registered or applied with. They see each application's progress in plain language, upcoming interviews with join link and calendar file, update their profile (skills, experience, city, notice, LinkedIn) across all applications, withdraw an application (interviews are cancelled and the team is emailed), re-download the resume they sent with each application, **download a copy of their data** (a JSON file with their applications, details, progress, interviews, emails sent and job alerts, without recruiter notes), and delete all their data (applications, resumes, job alerts, newsletter)
- **Employer portal** (`/employer`; `/employers/*` addresses lead here): one login per person, and a person can work in several companies (switch from the header). Roles per company: **Company owner** (everything, including the company profile, team, billing and the activity log), **Hiring manager** (posts jobs, edits and works the jobs assigned to them or that they posted), **Recruiter** (reviews applicants, changes their status and books interviews on assigned jobs) and **Viewer** (sees jobs and applicant progress without contact details). Every action is checked on the server against the person's role in the current company; another company's jobs and applicants are "not found". Pages: **Dashboard** (live/draft/waiting/paused/closed counts, new applicants, upcoming interviews, roles the team runs with stage counts, shortlists shared by the team, timesheets, placements and invoices), **Jobs**, **Applicants** (people who applied to the company's own jobs, filter by job and status, contact details and resumes only for people working on the job, status changes kept in each application's history), **Interviews** (book video, phone or in-person interviews; the candidate gets an invite), **Team** (invite by email, roles, assigned jobs, up to 50 people; the last owner can't leave), **Company** (profile, registration numbers, verification request) and **Settings** (name, mobile verification, password). The people working on a job are emailed when someone applies. Opening an applicant, downloading a resume, status changes, interviews, job changes and team changes go into the company's **activity log** (2 years). JSON: `GET/PATCH /api/employers/me`, `GET /api/employers/jobs/:id/applications`, `PATCH /api/employers/applications/:id/status`, `POST /api/employers/interviews`. Applicants to jobs the team runs for a client stay with the team, who share a shortlist. Passwords are hashed with scrypt, invite/reset links are single-use and expire, and logins are rate-limited
- **Applicant tracking** (employer portal **Pipeline**, `/employer/ats`): every application on the company's own jobs on a board (Applied → Screening → Shortlisted → Interview → Offer → Hired, plus On hold) or as a table, filtered by job, stage, skills, experience, location or "assigned to me". The board's forms and the API follow one workflow: each stage can only move to the next sensible ones, **Offer** needs an approved offer, **Hired** needs the candidate's acceptance, and withdrawn applications can't be moved. A company owner can **correct** a mistaken move with a written reason; the history keeps both the mistake and the correction, with who and when. Owners and hiring managers **assign** an application to someone working on the job. **Internal notes** are for the hiring team only and never appear in anything the candidate sees, their data download or emails. **Interviews** must be at least 2 hours ahead, between 7 am and 9 pm India time, and can't clash with the candidate's or the interviewer's other interviews; the candidate is invited and confirms or asks for another time from **My interviews**, and the people on the job are emailed. **Scorecards** can be written once the interview has started, by people working on the job; viewers don't see them. **Offers** (pay, joining date, location, notes) are made by a recruiter or manager, approved or turned down by a manager or owner (not the person who made it, unless they're an owner), then accepted or declined by the candidate, which the team records; the candidate is emailed the offer once it's approved. **Reports** (`/employer/ats/reports`, last 30, 90 or 365 days): active vacancies, applications, awaiting review, shortlisted, interviews, offers, hires, on hold, rejected and withdrawn, the stage funnel with conversion and drop-off, median time to hire (applied to hired) and time to fill (job live to first hire), results per job and, for managers and owners, each person's workload. Duplicate applications aren't counted twice. Every email the pipeline sends is recorded once per event, so a retry never emails anyone twice. Opening applicants, stage changes, corrections, notes, assignments, interviews, feedback and offer decisions go into the activity log. JSON: `GET /api/ats/jobs/:id/applications`, `GET /api/ats/applications/:id`, `PATCH /api/ats/applications/:id/stage`, `POST /api/ats/applications/:id/assign`, `POST /api/ats/applications/:id/notes`, `POST /api/ats/applications/:id/interviews`, `POST /api/ats/interviews/:id/feedback`, `POST /api/ats/applications/:id/offers`, `POST /api/ats/offers/:id/approve`, `POST /api/ats/offers/:id/response`, `GET /api/ats/analytics`. Match scores are shown to help people decide; nobody is rejected automatically
- **Notifications** (`/notifications`, for candidates, employer people and the team; the bell in each header shows how many are unread): one service sends every notification in-app and by email. Candidates hear when an application is received, when its status changes in a way they'd see, about interview invitations, new times, cancellations and reminders, offers and offer deadlines, new jobs matching their alerts, and password changes. Employer people hear about new applications to their jobs (marked "strong match" at 70%+ of the skills), applicants assigned to them, someone else moving their applicant, offers waiting for their approval, candidates confirming or asking to move an interview, feedback that is due, hires, decisions on jobs they sent for review, and jobs reaching their closing date. The team hears about new applications to jobs they own, jobs waiting for review (Admins), staffing requests, interview answers and feedback due. The center has All / Unread, filters for applications, interviews, jobs and account, mark one or all as read, and links to the job, applicant or interview. **Notification settings** (`/notifications/settings`) switch email for applications, interviews and jobs on or off; account, security, interview and offer emails to candidates always go. Recipients are worked out on the server from the records and people's current roles, so an employer never sees another company's candidates, and someone who loses access stops seeing the notifications. **Reliable delivery**: each email is saved as a delivery task in the same database write as the change that caused it, so an application or interview is saved even when the email provider is down; a background worker sends it and retries up to 5 times (after 1, 5, 30 and 120 minutes). Every event has a stable key, so a retry or a double click never sends twice. Sign-in links and interviewer feedback links are never stored, so they are sent straight away instead. **Job alerts**: at most one email per person per job however many of their alerts match, at most 10 a day, none when they switched job emails off (they still see it in-app). **Delivery reports**: set `EMAIL_WEBHOOK_SECRET` and have your provider (or a small relay) POST to `/webhooks/email` with an `x-hireriv-signature: t=<unix time>,v1=<HMAC-SHA256 of "<t>.<body>">` header and `{"events":[{"id","type":"delivered|bounced|complained|failed","messageId","recipient"}]}`; each event is processed once, and bounced or complaining addresses get no more notification emails. Admins see the queue, retries, failures and bounce rate under **Email delivery** (`/admin/notifications`), can retry failed emails, and the dashboard warns about failures, a stuck queue or a high bounce rate. Text messages, WhatsApp and browser notifications aren't used for notifications yet. JSON: `GET /api/notifications`, `GET /api/notifications/unread-count`, `PATCH /api/notifications/:id/read`, `POST /api/notifications/read-all`, `GET/PATCH /api/notification-preferences`, `GET/POST /api/job-alerts`, `DELETE /api/job-alerts/:id`. Employers and the team can also move an interview to a new time (same rules as booking); the candidate's calendar entry updates and they're asked to confirm again
- **SEO**: Google for Jobs structured data (JobPosting) on every open job, Organization/WebSite/BlogPosting data, `/sitemap.xml`, `/robots.txt`, canonical and Open Graph tags. Closed jobs are removed from the sitemap and marked `noindex`

## Data & backups
Everything the site stores (jobs, blog posts, settings, applications, requests, messages, subscribers, client accounts and sign-in sessions) lives in one SQLite database, `data/hireriv.db`, using the SQLite built into Node.js (22.13 or newer), so there is nothing extra to install. Resumes are saved in `uploads/`.

- **First start:** the database is created and filled from `data/jobs.json`, `data/posts.json` and `data/site.json`. Any older `data/submissions/*.json` files are imported once, and the originals are left untouched.
- **Backups:** the database is backed up automatically every day to a `backups` folder next to it (or `BACKUP_DIR`), with the newest 14 copies kept and listed under Admin → Settings → Backups. **Download database backup** there gives a copy on demand. Resumes in `uploads/` are not in the database, so back that folder up too.
- **Location:** set `DB_FILE` to keep the database somewhere else (e.g. a mounted disk).
- Client and candidate sign-ins are stored in the database, so restarting the server keeps everyone signed in.

### Optional: PostgreSQL copy of the jobs data
Set `DATABASE_URL` (e.g. `postgres://hireriv:password@localhost:5432/hireriv` in `.env`) and the site also keeps the jobs data in PostgreSQL: jobs, their places, categories (under the three kinds of work), skills, applications and saved jobs, in proper tables with keys, indexes and rules (pay minimum ≤ maximum, one live application per person per job, full-text search). SQLite stays the main store; leave `DATABASE_URL` unset and nothing changes.

- **Schema:** reviewed SQL files in `db/postgres/migrations/`. The server applies any pending ones when it starts (recorded in `schema_migrations`); `npm run pg:migrate` applies them ahead of a deploy.
- **Kept up to date:** every saved change is copied moments later, in one transaction, only the rows that changed. On start the server copies anything Postgres missed while it was away.
- **Search:** `GET /api/jobs` searches Postgres when it's connected and up to date, with the same filters, sorting and paging as the site. Keywords match the start of words ("dev" finds "developer"). If Postgres is down or behind, the API answers from the built-in search, and the site never waits for Postgres.
- **Privacy:** no names, emails or phone numbers go to Postgres. Applications and saved jobs carry a keyed one-way hash of the candidate instead.
- **Tests:** set `TEST_DATABASE_URL` to a Postgres where you may create schemas and `npm test` runs the Postgres tests too (each run uses its own schema and drops it). Without it they're skipped.

## Deploy
Hireriv is one Node.js process with a SQLite file, so any host that runs **Node 22.13+** with a **persistent disk** works. Keep the database and `uploads/` on that disk, and put the site behind HTTPS.

**Settings** – copy `.env.example` to `.env` and fill it in (`SITE_URL` with https, `ADMIN_PASS`, the `SMTP_*` values, `TRUST_PROXY=1` behind a proxy). Run with `npm run start:env`, or set the same variables in your host's dashboard. With `NODE_ENV=production` the server prints a warning at startup for anything important that is missing.

**Docker** (on a VPS):
```bash
docker build -t hireriv .
docker run -d --name hireriv -p 3004:3004 --env-file .env -v hireriv-data:/var/lib/hireriv --restart unless-stopped hireriv
```
The image keeps the database and resumes in the `hireriv-data` volume and checks `/healthz` every 30 seconds. Put Nginx or Caddy in front for HTTPS.

**Render / Railway** – create a Node web service from this repo (build: `npm ci`, start: `node server.js`), attach a persistent disk mounted at e.g. `/var/data`, and set `DB_FILE=/var/data/hireriv.db`, `UPLOADS_DIR=/var/data/uploads`, `TRUST_PROXY=1` plus the settings above. Use `/healthz` as the health check path.

**Built in:** security headers (Content-Security-Policy with no inline scripts, anti-framing, nosniff, referrer and permissions policies, HSTS on https), `/healthz` (checks the database), private areas hidden from search engines, and cache-busted CSS/JS.
